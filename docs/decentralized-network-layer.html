The Network Layer — Decentralized, Encrypted, Delivery-Verified

A design for P2P identity, full end-to-end encryption, near-guaranteed delivery, and partition tolerance.

Using the right web3 primitives — and deliberately not a global consensus blockchain.

Network-layer design · 23 Jul 2026
The single design decision everything hangs on: you want blockchain-grade verifiability (tamper-proof identities, provable delivery) without blockchain-grade consensus. A global chain needs the exact connectivity a disaster destroys, and its "wait for global agreement" model is the opposite of "fast completeness." The answer is local-first cryptography: signed hash-linked logs + signed receipts + CRDTs. These give you provable, tamper-evident delivery that works fully offline and converges the instant links reappear. Keep an actual ledger — if you use one at all — only for incentives/settlement, running opportunistically when online.

1 · The layered stack

Seven layers. Each one is a well-studied problem with mature open-source parts — you're assembling, not inventing.

Green layers (L2, L5) + amber L6 are the cryptographic heart — all function offline. A ledger, if used, sits only inside L6 for incentives and settles when online.

2 · Solving your four hard problems

Problem A — Identify peers & guarantee full end-to-end encryption

Every user generates a keypair on-device; the address is the public key (self-sovereign identity — the web3 "DID" idea, no registrar, no phone number). Two peers exchange keys out-of-band once (QR scan, like Briar) or discover them via the DHT/announces. Messages use X3DH to agree a key asynchronously and the Double Ratchet (the Signal design) for forward secrecy, wrapped in sealed sender so relays can't even see who sent what.

Because encryption is end-to-end at L2, every relay and gateway above only ever handles opaque ciphertext. Full encryption isn't a feature bolted on — it's the identity system itself. This is the only layer that ever sees plaintext, and it runs solely on the two endpoints.

Problem B — Make every message reach its recipient

In a partition-prone network you can't promise bounded-time delivery, but you can engineer eventual delivery with very high probability, plus proof of it:

  • Replication (spray-and-wait): the message is carried as a small number of controlled copies, not one fragile packet — dramatically raising delivery odds without flooding.
  • Custody transfer (from DTN Bundle Protocol): a node formally takes responsibility for a message before the previous holder drops it — no silent loss at hand-offs.
  • End-to-end signed receipt: the recipient, on decrypting, emits a signed acknowledgement that propagates back. Until the sender sees it, the message is retried on new paths.
  • TTL + priority: messages are patient (long TTL) and emergencies preempt everything at every hop.
Honesty check: "every message always arrives" is physically impossible if a recipient is permanently unreachable. The achievable, defensible guarantee is: delivered with high probability, and when delivered, cryptographically proven — and the sender always knows which of the two it is. That certainty is what users actually need.

Problem C — A whole region's links are down (can't get messages in or out)

No algorithm beats physics: if zero links cross the boundary, no bits cross. So the design maximizes the chance that some link exists, and stays useful in the meantime:

  • Transport diversity = more chances of one live link: sound/light locally, BLE/Wi-Fi mesh, LoRa for km-scale, internet where any node has it. The more independent physical channels, the harder it is to fully seal a region.
  • Humans as the link (data mules): anyone who walks or drives out of the zone carries queued messages on their phone and flushes them the moment they hit connectivity — a car leaving a flood zone is a network link. This is the DTN "sneakernet" principle and it's remarkably robust.
  • Erasure/fountain coding across mules: split a message into coded fragments so it reconstructs even if only some carriers make it out — resilient to partial escape.
  • The region keeps working internally: intra-region messaging never stops; only cross-boundary traffic queues. Patient queues flush automatically when any boundary link reappears.
  • Pre-positioned independent gateways: solar-powered LoRa nodes on high ground that don't depend on the grid or towers — deliberate "always-on straws" out of the region.
Reframe: a sealed region isn't a failure state, it's a buffering state. The network holds every message safely, keeps the locals talking, and delivers outward the instant the first mule, solar node, or restored link bridges the gap — then CRDT merge (below) reconciles both sides in seconds with zero conflicts.

Problem D — Web3-style validation + fast completeness (without the consensus tax)

This is where your blockchain instinct pays off — used precisely. Three primitives give you tamper-proof, verifiable delivery that needs no global agreement:

  1. Hash-linked per-identity logs (Merkle feeds): each user's outbox is an append-only log where every entry references the hash of the previous one (like git / Secure Scuttlebutt / a personal mini-chain). Tamper-evident, self-verifying, no miners — anyone can check it, and two copies sync by exchanging only what's missing.
  2. Signed delivery receipts: the recipient's signature over a message's hash is portable, standalone proof of delivery — verifiable by anyone, offline, forever. No ledger required to trust it.
  3. CRDTs for "fast completeness": shared state (delivery status, group membership, presence) is modelled as conflict-free replicated data types (Automerge/Yjs-style). Every node is instantly consistent locally, and when partitions heal the states merge deterministically with no conflicts — convergence in one sync round, not one block time. That is fast completeness.
DELIVERY VALIDATION FLOW (all offline-capable):
1 · Sender S encrypts msg → recipient R's key; appends hash(msg) to S's signed log
2 · Relays carry it (spray-and-wait); each may add a signed custody receipt
3 · R decrypts, emits Receipt = Sign_R( hash(msg), timestamp )
4 · Receipt diffuses back opportunistically → S matches it to the log entry
5 · S now holds cryptographic proof of delivery — no chain, no consensus, works fully offline
6 · (optional) aggregated custody/delivery receipts = proof-of-relay, settled to a ledger later, when online, to reward gateways
The only place a real distributed ledger earns its keep is the optional incentive layer (rewarding people who run gateways/relays — the Helium / "proof-of-relay" model). Crucially it settles asynchronously when online, so it never sits in the delivery path or slows anything down. Delivery correctness comes entirely from signatures, not consensus.

3 · Handling misuse (you flagged this explicitly)

AbuseDefense
Spam / floodingProof-of-work "postage" per message (Hashcash), scaled by priority; cheap for a real user, expensive at scale. Rate limits at relays.
Sybil (fake identities)Identity creation costs PoW; reputation is earned via successful relays; high-trust contacts via web-of-trust vouching / QR key exchange.
Black-hole relays (drop messages)Replication + missing end-to-end receipts expose non-delivery; reputation gossip demotes bad relays; traffic re-routes around them.
Harmful contentNetwork is content-blind by design (E2E), so moderation lives at the endpoints: report/block keys, gossiped blocklists, key-level bans. tradeoff Honest tension between privacy and moderation — decide the policy deliberately.
Gateway DoS (scarce exits)Priority classes (SOS preempts chatter) + per-sender fair-queuing + PoW so no one can monopolize a gateway.

Net effect: build on Reticulum for L1–L4, layer SSB-style hash-linked logs + Automerge CRDTs for L5, add your PoW/reputation + optional proof-of-relay at L6, and keep the Double Ratchet at L2. That's roughly 80% assembly of hardened components and 20% new glue — the new glue being your delivery-receipt protocol, the sound/light interfaces, and the incentive design.
Design brief, not final spec — verify before building. Confirm licenses (SSB, Automerge, Reticulum, libsignal) for your product model; libsignal in particular has usage terms. The Double Ratchet fits interactive chat cleanly but needs care for long-delay/one-way DTN paths — validate the async/sealed-sender variant against your worst-case delivery latency. Physics caveat stands: a permanently isolated recipient cannot receive; the system's job is to prove whether delivery happened, not to defy that.
